# Domain Entities (`app/controllers/`)

This document describes the **shared domain entities** the application exposes through `app/controllers/`. For the rules governing how these folders must be structured (barrels, layering, raw types staying private, etc.), see [`controllers-architecture.md`](./controllers-architecture.md). For the underlying database schema these entities ultimately project from, see [`../ENTIDADES.md`](../ENTIDADES.md).

The naming of the domain stays in Spanish (`Paciente`, `Terapeuta`, `Tratamiento`, `Diagnostico`, `Contenido`) because that is how the business names its actors. Technical prose is in English.

Each section below describes one entity folder and follows the same shape:

- **What it is** — the role this entity plays in the Aurora domain.
- **Status** — the maturity of its public contract (types only / types + read hook / etc.).
- **Public API** — what `index.ts` exports today. Anything not listed here is private to the folder and must not be imported from outside.
- **Field table** — fields of the main exported interface.
- **When to use** — the domain situations in which this entity is the right vocabulary to reach for.

Entities are listed alphabetically.

## AdminDashboard

**What it is.** Read-only analytics aggregate for the administration dashboard: network-wide totals + global distributions that span Paciente + Diagnostico + Tratamiento and belong to no single existing entity. Created via the Rule 6 gate (explicit user approval) precisely because the data is cross-cutting; the per-terapeuta rollup lives under `Terapeuta`, but the network aggregate is its own concern.

**Status.** Types + one read hook + mapper + fetcher. Functional. Backed by the `get_admin_dashboard_stats()` RPC (jsonb, `is_admin()` guard).

**Public API** (`app/controllers/AdminDashboard/index.ts`):

- `AdminDashboardStats` (type) — the mapped aggregate (see fields below).
- `DistItem` (type) — `{ label: string; cantidad: number; pct: number }`. Structurally identical to the dashboard's presentation `DistItem`; defined here so the entity does not depend on the route group.
- `useFetchAdminDashboardStats()` — hook returning `{ stats: AdminDashboardStats | null, isLoading: boolean, error: string | null, refresh: () => void }`. Calls `supabase.rpc('get_admin_dashboard_stats')`. Admin only — a terapeuta receives `no_autorizado` (42501) surfaced via `error`. `stats` is `null` until resolved.
- `UseFetchAdminDashboardStatsResult` (type) — the return shape of `useFetchAdminDashboardStats`.

Internals (`utils/mapAdminDashboardStats.ts` with its private `AdminDashboardStatsRaw` type, `api/fetchAdminDashboardStats.ts`) are private to the folder and must not be imported from outside.

**`AdminDashboardStats` fields:**

| Field               | Type                      | Meaning                                                                                               |
| ------------------- | ------------------------- | ----------------------------------------------------------------------------------------------------- |
| `pacientesActivos`  | `number`                  | Pacientes en estado `activo` (con asignación vigente) en toda la red; pausados y bajas no cuentan.    |
| `nuevosEsteMes`     | `number`                  | De esos, los dados de alta en el mes calendario actual.                                               |
| `alertasTotales`    | `number \| null`          | Pacientes activos con último score ≤ 3. `null` si ningún paciente activo tiene evaluaciones (Tier B). |
| `scorePromedio`     | `number \| null`          | Promedio del último score (1 decimal). `null` si no hay evaluaciones (Tier B).                        |
| `distribucionCausa` | `ReadonlyArray<DistItem>` | Pacientes activos por causa raíz (con `pct` calculado en el mapper).                                  |
| `distribucionEtapa` | `ReadonlyArray<DistItem>` | Pacientes activos por etapa (`ceil(nivel_actual/2)`, `"Sin nivel"`), `pct` en el mapper.              |

All fields are `readonly`. `pct` is computed client-side in the mapper (the RPC returns only `label` + `cantidad`).

**When to use.**

- Solo el dashboard de administración (`app/(dashboard)` con rol admin). Para la carga/salud por terapeuta usá `useFetchTerapeutasDashboard` de `Terapeuta`; para el agregado de la red usá este hook.
- No es el lugar para datos de un terapeuta o paciente individual — esos viven en `Terapeuta` / `Paciente`.

## Alerta

**What it is.** Cross-cutting derived signal that surfaces "which paciente needs attention now" — score bajo, evaluación vencida, mes 3, cerca del cierre, reinicio de tratamiento. Computed server-side on every read by `derive_alertas_activas()` (no row is persisted for the alert itself; only the dismissal is). Spans Paciente + Tratamiento and belongs to no single existing entity. **Pre-approved via Rule 6** (DEC-E0-4, precedent: `AdminDashboard`) — re-creating this folder does not re-trigger the gate.

**Status.** Types + catalog read hook (`useFetchTiposAlerta`) + private row mapper (`mapAlertaRow`) + the terapeuta read hook (`useFetchAlertasTerapeuta`) + the admin drill-down read hook (`useFetchAlertasByTerapeuta`) + the mutation hook (`useMarcarAlertaAtendida`) + the personal count hook for the global shell badge (`useAlertasCount`). `reinicio` (5th tipo, `baja` priority) was reincorporated in `feat/nuevo-tratamiento` (Epic 3 Task 3.2, DEC-33) after being descoped from the original MVP. `contenido_pendiente` (6th tipo, `media` priority) was added in `feat/inicio-tratamiento` (Epic 2 Task 2.2) and then **removed** in the same branch (DEC-12, post-implementation product reversal): redundant with the therapist's own "Sin iniciar" onboarding widget on their dashboard — the admin's compensation is the new `sin_iniciar` column on `Terapeuta`/`/terapeutas` instead (see the `Terapeuta` entity below). The engine is back to 5 tipos.

**Public API** (`app/controllers/Alerta/index.ts`):

- `Alerta` (type) — the mapped domain shape of one active alert (see fields below).
- `AlertaPrioridad` (type) — `'alta' | 'media' | 'baja'`.
- `ALERTA_TIPO` (enum) — `SCORE_BAJO`, `EVAL_VENCIDA`, `MES_3`, `FIN`, `REINICIO`.
- `TipoAlerta` (type) — one row of the `tipos_alerta` presentation catalog: `{ codigo, nombre, prioridad: AlertaPrioridad, orden: number, icono: string, descripcion: string | null, activo: boolean }`.
- `mapAlertaRow(row, catalogo: ReadonlyArray<TipoAlerta>): Alerta` — maps the private 8-column RPC row to `Alerta`. Resolves `prioridad`/`nombre`/`icono` by looking up `row.tipo` against `catalogo[].codigo` (kills the v1 split-brain where these were hardcoded in TS). Falls back to `prioridad: 'media'`, `nombre: row.tipo`, `icono: '?'` when the tipo has no catalog match. Templates `mensaje` in TS by tipo: `score {valor} · última evaluación`, `evaluación vencida`, `entra en mes 3`, `cerca del cierre`, `reinició tratamiento`; unknown tipo → `alerta pendiente de revisión`. Exported so Epic 1/2 fetchers (which own the actual RPC call) can reuse it.
- `useFetchTiposAlerta()` — hook returning `{ tipos: ReadonlyArray<TipoAlerta>, isLoading: boolean, error: string | null }`. Reads `tipos_alerta` ordered by `orden`. No `refresh()` — the catalog is static/read-only.
- `useFetchAlertasTerapeuta()` — hook returning `{ alertas: ReadonlyArray<Alerta>, isLoading: boolean, error: string | null, refetch: () => void }`. Composes `useFetchTiposAlerta()` (catalog) with the `list_alertas_terapeuta()` RPC (no params — scoped server-side by `auth.uid()`), mapping every row via `mapAlertaRow`. `isLoading` is true while either the catalog or the alertas fetch is in flight; `error` surfaces the catalog error first, then the alertas fetch error. `refetch()` only re-runs the alertas fetch (the catalog is static) — call it after `marcar`/`desmarcar` to reconcile the inbox.
- `useFetchAlertasByTerapeuta(terapeutaId: string | null)` — hook returning `{ alertas: ReadonlyArray<Alerta>, isLoading: boolean, error: string | null }`. Admin drill-down (the "Alertas" column of `/terapeutas`, Epic 2): composes `useFetchTiposAlerta()` with the `list_alertas_admin({ p_terapeuta_id: terapeutaId })` RPC (`is_admin()` guard server-side), mapping every row via `mapAlertaRow`. Null-guards like `useFetchTerapeutaById` — does not fetch (and returns `{ alertas: [], isLoading: false, error: null }`) while `terapeutaId` is `null`. Read-only: no `refetch`, since there is no mutation on this surface to reconcile. The RPC filters `derive_alertas_activas()` by the same `terapeuta_id` that feeds `list_terapeutas.alertas_activas` — the two counts are guaranteed to match for a given terapeuta (validated by psql in Task 2.1).
- `useMarcarAlertaAtendida()` — hook returning `{ marcar, desmarcar, isMarcando: boolean, error: string | null }`. Both `marcar(tipo: ALERTA_TIPO, eventoRef: string, pacienteId: string)` and `desmarcar(tipo, eventoRef, pacienteId)` return `Promise<{ error: string | null }>` and call the `marcar_alerta_atendida` / `desmarcar_alerta_atendida` RPCs respectively (same 3-param signature: `p_tipo`, `p_evento_ref`, `p_paciente_id`). Both RPCs enforce `has_active_assignment(pacienteId)` server-side (`42501` if not owner) and `marcar_alerta_atendida` validates `tipo` against the 5 vigentes values (`23514` if invalid) — the hook does not duplicate that validation. `isMarcando` and `error` are shared across both verbs (not tracked per-call). Consumers must call `useFetchAlertasTerapeuta`'s `refetch()` after a successful `marcar`/`desmarcar` to reflect the change in the inbox — this hook does not do it automatically.
- `useAlertasCount()` — hook returning `{ count: number, isLoading: boolean, error: string | null, refetch: () => void }`. Calls the lightweight `count_alertas_terapeuta()` RPC (no params, scoped server-side by `auth.uid()` — see Epic 3 Task 3.1). **Personal for every role** (an admin, treated as a terapeuta, counts their own caseload) — does not branch by role and has no admin counterpart (network-wide supervision lives in the `/terapeutas` "Alertas" column instead, via `useFetchAlertasByTerapeuta`). Meant to back the global shell badge (`Topbar` → `AlertasCountBell`, Epic 3 Task 3.3), so it refetches on **mount**, on **window `focus`**, and on **route change** (`usePathname()` from `next/navigation` sits in the effect's dependency array — the hook re-runs whenever the consuming component re-renders across a navigation, no prop needed from the shell). This is eventual consistency, not realtime: after marking/unmarking in `/alertas`, the badge reconciles on the next of these refetches. On RPC error, `count` is **not** reset (keeps the last known value) and only `error` is set — the consumer is expected to treat a truthy `error` as "hide the badge", degrading gracefully instead of breaking the page. `refetch()` (BETA-028) re-runs the count on demand, for actions that change it **without** changing route (closing a tratamiento switches some alertas off and may switch others on while the terapeuta stays on the same screen).
- `UseFetchTiposAlertaResult`, `UseFetchAlertasTerapeutaResult`, `UseFetchAlertasByTerapeutaResult`, `UseMarcarAlertaAtendidaResult`, `UseAlertasCountResult` (types) — the return shapes of the five hooks above. `MarcarAlertaResult` (type) — `{ error: string | null }`, what `marcar` / `desmarcar` resolve to.

Internals (`utils/mapAlertaRow.ts` with its private `AlertaRow` type, `api/fetchTiposAlerta.ts`, `api/fetchAlertasTerapeuta.ts`, `api/fetchAlertasByTerapeuta.ts`) are private to the folder and must not be imported from outside.

**`Alerta` fields:**

| Field             | Type              | Meaning                                                                               |
| ----------------- | ----------------- | ------------------------------------------------------------------------------------- |
| `tipo`            | `ALERTA_TIPO`     | Which of the 5 alert kinds this is.                                                   |
| `prioridad`       | `AlertaPrioridad` | `'alta'`, `'media'`, or `'baja'`, resolved from the `tipos_alerta` catalog.           |
| `pacienteId`      | `string`          | The paciente the alert is about.                                                      |
| `pacienteNombre`  | `string`          | Display name of the paciente.                                                         |
| `terapeutaId`     | `string`          | The terapeuta whose caseload owns the paciente.                                       |
| `terapeutaNombre` | `string \| null`  | `null` in the terapeuta's own inbox view (self-evident); populated in the admin view. |
| `nombre`          | `string`          | Human label for the tipo, resolved from the catalog (e.g. `"Score bajo"`).            |
| `icono`           | `string`          | Glyph for the tipo, resolved from the catalog (e.g. `↘`, `?`, `✦`).                   |
| `mensaje`         | `string`          | Templated message for the specific event (see `mapAlertaRow` above).                  |
| `eventoRef`       | `string`          | Opaque reference to the underlying event row (nivel, evaluacion, or etapa+suffix).    |
| `fecha`           | `string \| null`  | ISO date relevant to the alert, or `null` when not applicable.                        |

All fields are `readonly`.

**`TipoAlerta` fields:** `codigo` (PK, matches `Alerta['tipo']` values), `nombre`, `prioridad`, `orden` (presentation ordering), `icono`, `descripcion` (nullable), `activo`.

**When to use.**

- Any surface that lists or counts active alerts (the `/alertas` inbox, the admin drill-down, the notification bell) reaches for this entity — never queries `derive_alertas_activas()` or `tipos_alerta` directly from a ViewModel.
- Use `useFetchTiposAlerta` whenever a component needs the catalog metadata directly (e.g. building a filter chip list by `orden`); use `mapAlertaRow` only from within this entity's own `api/` fetchers (Epic 1/2), never from a ViewModel.
- Any `Record<Alerta['prioridad'], ...>` (e.g. `PRIORIDAD_ORDEN` in `useAlertasViewModel.ts`, `TONE_BY_PRIORIDAD` in `components/alertas/AlertaTipoIcon.tsx`) must cover `'baja'` — TypeScript's exhaustive `Record` check catches any consumer that doesn't.

## Auth

**What it is.** The identity layer. Owns the shape of a logged-in user's profile, the canonical platform roles, and the single sanctioned seam for resolving the current user inside ViewModels.

**Status.** Types + read hook. Functional.

**Public API** (`app/controllers/Auth/index.ts`):

- `useCurrentUserId()` — returns `{ userId: string | null, error: string | null, isLoading: boolean }`. Reads the Supabase session via `supabase.auth.getUser()` and exposes the user id as a React state. **This is the only place in the app permitted to call `supabase.auth.getUser()`.**
- `useCurrentUserProfile()` — returns `{ profile: Profile | null, isLoading: boolean, error: string | null }`. Composes `useCurrentUserId` internally; when a `userId` is available, queries `profiles` with `roles(codigo)` and hydrates `email` via `supabase.auth.getUser()`. **Any ViewModel that needs the logged-in user's full profile — including role — must call this hook; never query `profiles` directly from a ViewModel.**
- `resolveRole(codigo: string | undefined): ROLE` — maps a raw `roles.codigo` string to the `ROLE` enum. Defaults to `ROLE.PACIENTE` for unknown or missing values. Shared by all entities that join the `roles` table (e.g. `Terapeuta`).
- `rutaInternaSegura(ruta: string | null, porDefecto: string): string` — returns `ruta` only when it is an internal path of the panel (starts with a single `/`, no `//`, no backslash, no control characters); anything else returns `porDefecto`. Use it on every redirect target that comes from the URL (`/auth/confirm?next=…`) so a crafted link cannot send the user off-site.
- `mapAuthError(err: unknown): string` — translates a Supabase Auth error into the Spanish copy the panel shows (BETA-004). Looks the message up by `err.code` first and by `err.name` second, both through a `Map`; anything unknown returns the generic "Algo salió mal. Probá de nuevo.". Never shows the raw English `message`. Used by the auth ViewModels and by `/auth/error`, which receives the `code` in the query string.
- `mapLoginUrlError(codigo: string | null): string | null` — translates the `?error=` code of `/auth/login` into the copy the login shows (seguridadPanel / SEG-003). Only known codes, through a `Map`: `sin_acceso` (written by the proxy and by `useExpulsarSesionInvalida` when the session is not console), `sesion_terminada` and `cuenta_desactivada` (written by `useExpulsarSesionInvalida`, BETA-045); anything else returns `null`, so text from the URL is never reflected. Used by `useLoginViewModel`.
- `useExpulsarSesionInvalida({ activo, pathname })` — returns `{ expulsando: boolean }` (pulidoBeta / BETA-045). Shell-only hook (called from `useSidebarViewModel`): on mount and on every `pathname` change while `activo`, asks Auth whether the session is still alive (`supabase.auth.getUser()`) and the database whether the user is still console (`is_console_user`). On an explicit rejection it signs out **this browser only** (`signOut({ scope: 'local' })`) and `router.replace('/auth/login?error=<code>')`; `expulsando` is `true` in between so the shell does not paint an empty panel. Network errors, 5xx and anything it does not understand never expel (fail-open, like the proxy). This is the second sanctioned caller of `supabase.auth.getUser()`, inside the Auth entity.
- `UseCurrentUserProfileResult` (type) — the return shape of `useCurrentUserProfile`.
- `Profile` (type) — the user profile shape used across the app.
- `ROLE` (enum) — the canonical role values.

**`Profile` fields:**

| Field      | Type     | Meaning                                                   |
| ---------- | -------- | --------------------------------------------------------- |
| `id`       | `string` | Supabase auth uuid (matches `auth.users.id`).             |
| `name`     | `string` | Display name.                                             |
| `role`     | `ROLE`   | One of `ADMIN`, `TERAPEUTA`, `PACIENTE`.                  |
| `timezone` | `string` | IANA timezone, drives scheduling of niveles and entregas. |
| `email`    | `string` | Email address.                                            |

**`ROLE` values:** `ADMIN`, `TERAPEUTA`, `PACIENTE`. `PACIENTE` is kept for completeness of the model — a `paciente` is never a user of this web console, only a subject of treatment.

**When to use.**

- Any ViewModel that needs the logged-in user's id **must** call `useCurrentUserId`. ViewModels are forbidden from calling `supabase.auth.getUser()` directly (see Rule 5 of `controllers-architecture.md`).
- Any ViewModel that needs the logged-in user's **full profile** — including name, timezone, email, and role — **must** call `useCurrentUserProfile`. Never query the `profiles` table directly from a ViewModel.
- Any code that needs to talk about "the role of a user" uses `ROLE`, not raw string literals.
- When mapping a raw DB row that contains a `roles.codigo` join, use `resolveRole` from `@/app/controllers/Auth` — do not define a local copy in another entity.
- The `Profile` type is the shape every consumer of "the user behind a row" should reach for; entities like `Terapeuta` embed it rather than redeclaring its fields.

## Contenido

**What it is.** A unit of therapeutic content delivered to a `Paciente` as part of a weekly entrega: video/audio/gallery media from the `contenidos` table. Five tipos: `VIDEO`, `AUDIO`, `EGREGOR` (media, same pipeline as video), `CMA` and `IC` (image galleries backed by `contenido_imagenes`). The `TEXTO` variant (motivational phrases) is a **retired vestige**: the manual frase ABM — route, hooks, mappers, and RPCs (`frases_motivacionales` table, `frase_id` columns) — was removed in frasesAutomaticas/epic-4 (task-4.1 dropped the DB side, task-4.2 dropped the app side). `TIPO_CONTENIDO.TEXTO` and the `Contenido` union's `TEXTO` arm are kept intentionally for now (frasesAutomaticas/epic-4, task-4.3 collapses the type) — do **not** wire any new frase read/write path against them; no `TEXTO` row can ever be produced anymore.

**Status.** Types (5 media/gallery tipos + vestigial `TEXTO`) + two read hooks (all contenido, by-id contenido, both now embedding ordered gallery images) + two signed-URL hooks (`useFetchContenidoMediaUrl` single, `useFetchContenidoImagenesUrls` gallery-batch) + five mutation hooks (create/update/count/delete/replace contenido) + two gallery-specific mutation hooks (`useCreateContenidoGaleria`, `useSetContenidoImagenes`) + one upload hook for galleries (`useUploadContenidoImagenes`, direct-to-Storage, no Uppy/TUS — see `architecture/image-upload-strategy`) + one raw-row mapper + `refresh()` on the all-list hook. Functional. **cma/ic rows are created EXCLUSIVELY via `useCreateContenidoGaleria` → `create_contenido_galeria`** — `useCreateContenido` → `create_contenido` keeps its non-nullable `recursoRef: string` and unconditionally rejects a null/blank `recurso_ref` for all five tipos (`recurso_ref_vacio`); this is a hardened invariant, not an oversight — see `sdd/new-media-types/spec-correction-01`.

**Barrel/catalog note.** `mapContenidoRow` and its raw type `ContenidoRowRaw` ARE re-exported from `index.ts` today (consumed directly by `Tratamiento/utils/mapEtapaToTratamientoConEntregas.ts`, which maps an embedded `contenidos` row coming from a different query root). This deviates from Rule 5's "raw types never leave the entity" — pre-existing drift, not introduced by this catalog update; flagged here per the barrel-wins rule instead of silently re-hiding an export something else already depends on.

**Public API** (`app/controllers/Contenido/index.ts`):

- `Contenido` (type) — `ContenidoMetadata & { tipo: VIDEO | AUDIO | EGREGOR | CMA | IC; contenido: MediaContent; imagenes: ReadonlyArray<ContenidoImagen> }`. `imagenes` is always `[]` for non-gallery tipos.
- `ContenidoMetadata` (type) — `{ readonly id: string; readonly titulo: string | null; readonly descripcion: string | null }`. Shared base across all variants.
- `MediaContent` (type) — `{ readonly recursoRef: string | null; readonly duracion: number | null }`. Null for CMA/IC (galleries carry no single media ref).
- `ContenidoImagen` (type) — `{ readonly path: string; readonly orden: number }`. One gallery image, `orden` ascending. Server-derived on create (`with ordinality` over the upload array) — never client-set.
- `TIPO_CONTENIDO` (enum) — `VIDEO`, `AUDIO`, `EGREGOR`, `CMA`, `IC`, `TEXTO` (`TEXTO` vestigial, see above).
- `useFetchAllContenido()` — hook returning `{ contenidos: ReadonlyArray<Contenido>, isLoading: boolean, error: string | null, refresh: () => Promise<void> }`. Reads `contenidos` table filtered by `activo = true`, embedding `contenido_imagenes(path, orden)`. Rows whose `tipo` is not one of the 5 supported values are silently skipped. `refresh()` re-invokes the fetcher in background without flipping `isLoading`.
- `useFetchContenidoById(contenidoId: string | null)` — hook returning `{ contenido: Contenido | null, isLoading: boolean, error: string | null }`. Noops on null; returns `contenido = null` when the row's `tipo` is unsupported, when the row is missing, or when `activo = false`. Embeds `contenido_imagenes(path, orden)` like the list hook.
- `useCreateContenido()` — mutation hook returning `{ mutate, isLoading, error }` where `mutate({ tipo, titulo, descripcion, recursoRef, duracionSeg })` calls `supabase.rpc('create_contenido', { p_tipo, p_titulo, p_descripcion, p_recurso_ref, p_duracion_seg })`. `tipo` is `VIDEO`/`AUDIO`/`EGREGOR` (sent lowercased to RPC); `recursoRef: string` stays non-nullable — the RPC unconditionally rejects a null/blank ref for ALL tipos, cma/ic included, so this hook must never be called for `CMA`/`IC` (use `useCreateContenidoGaleria` instead). On success returns `{ ok: true, contenido: Contenido }`; on error returns `{ ok: false }` and surfaces the raw RPC error code in `error`. Known codes: `'no_autorizado'`, `'tipo_invalido'`, `'titulo_vacio'`, `'recurso_ref_vacio'`; fallback `'create_failed'`.
- `useCreateContenidoGaleria()` — mutation hook returning `{ mutate, isLoading, error }` where `mutate({ tipo: CMA | IC, titulo, descripcion, paths })` calls `supabase.rpc('create_contenido_galeria', { p_tipo, p_titulo, p_descripcion, p_paths })`, atomic across `contenidos` + `contenido_imagenes` on the server (`orden` derived from `p_paths` array order via `with ordinality` — the client never sends `orden`). On success returns `{ ok: true, contenido: Contenido }`, reconstructing `imagenes` from `p_paths` (index+1 = orden) without a second round-trip. On error returns `{ ok: false }`. Known codes: `'no_autorizado'`, `'tipo_invalido'`, `'titulo_vacio'`, `'galeria_vacia'`; fallback `'create_galeria_failed'`. This is the ONLY sanctioned path to create a CMA/IC row.
- `useSetContenidoImagenes()` — mutation hook returning `{ mutate, isLoading, error }` where `mutate({ contenidoId, paths })` calls `supabase.rpc('set_contenido_imagenes', { p_contenido_id, p_paths })` — a full-replace of a gallery's images (delete-then-upsert on the server, `orden` re-derived from `paths` order). On success returns `{ ok: true, removedPaths: ReadonlyArray<string> }` — the caller is responsible for a best-effort Storage purge of `removedPaths`. On error returns `{ ok: false, removedPaths: [] }`. Known codes: `'no_autorizado'`, `'galeria_vacia'`, `'no_encontrado'`; fallback `'set_imagenes_failed'`.
- `useUpdateContenido()` — mutation hook returning `{ mutate, isLoading, error }` where `mutate({ id, titulo, descripcion })` calls `supabase.rpc('update_contenido', { p_id, p_titulo, p_descripcion })`. On success returns `{ ok: true, contenido: Contenido }`; on error returns `{ ok: false }`. Known codes: `'no_autorizado'`, `'titulo_vacio'`, `'no_encontrado'`; fallback `'update_failed'`.
- `useCountContenidoUsage()` — mutation hook returning `{ mutate, isLoading, error }` where `mutate({ id })` calls `supabase.rpc('count_contenido_usage', { p_id })`. On success returns `{ ok: true, count: number }` (count = distinct patients with the contenido in their plan). On error returns `{ ok: false }`. Known codes: `'no_autorizado'`; fallback `'count_contenido_failed'`.
- `useDeleteContenido()` — mutation hook returning `{ mutate, isLoading, error }` where `mutate({ id })` calls `supabase.rpc('delete_contenido', { p_id })`. On success returns `{ ok: true }` (physical delete). On error returns `{ ok: false }`. Known codes: `'en_uso'`, `'no_encontrado'`, `'no_autorizado'`; fallback `'delete_contenido_failed'`.
- `useReplaceAndDeleteContenido()` — mutation hook returning `{ mutate, isLoading, error }` where `mutate({ oldId, newId })` calls `supabase.rpc('replace_and_delete_contenido', { p_old_id, p_new_id })`. On success returns `{ ok: true, affected: number }` (affected = distinct patients reassigned). On error returns `{ ok: false }`. Known codes: `'tipo_distinto'`, `'no_encontrado'`, `'no_autorizado'`; fallback `'replace_contenido_failed'`.
- `useFetchContenidoMediaUrl(recursoRef: string | null)` — hook returning `{ src: string | null, isLoading: boolean, error: string | null, retry: () => void }`. Generates a signed URL (TTL 3600 s) from the `contenidos` private bucket via `supabase.storage.from('contenidos').createSignedUrl(recursoRef, 3600)`. When `recursoRef` is `null` (legacy item, or any CMA/IC row), returns idle state immediately without calling Storage. On success sets `src` to the signed URL. On storage error or null data, sets `error = 'signed_url_failed'`. `retry()` increments an internal nonce that re-triggers the effect, forcing URL re-generation. No global cache — URL is regenerated on detail load and on each retry (per DEC-14, DevSpec §8.4).
- `UseFetchContenidoMediaUrlResult` (type) — return shape of `useFetchContenidoMediaUrl`.
- `useFetchContenidoImagenesUrls(paths: ReadonlyArray<string>)` — hook returning `{ urls: ReadonlyArray<{ path: string; signedUrl: string }>, isLoading: boolean, error: string | null }`. Signs every gallery path in one Storage round-trip via `createSignedUrls` (plural, TTL 3600 s) from the `contenidos-imagenes` bucket, instead of one `createSignedUrl` call per image. Idle (`urls: []`) when `paths` is empty, without calling Storage. Same `cancelled`-guard cleanup posture as `useFetchContenidoMediaUrl`; re-fetches when the `paths` array's joined contents change (dependency is `paths.join(',')`, not array identity, so a fresh inline array literal per render does not re-trigger the effect).
- `UseFetchContenidoImagenesUrlsResult`, `SignedImagen` (types) — return shape / element type of `useFetchContenidoImagenesUrls`.
- `useUploadContenidoImagenes(tipo: 'cma' | 'ic')` — hook returning `{ items: ReadonlyArray<UploadItem>, addFiles, retry, remove, reset, successfulPaths: ReadonlyArray<string>, canSubmit: boolean }`. Direct client→Storage upload to `contenidos-imagenes` (`supabase.storage.from('contenidos-imagenes').upload(objectName, file, { contentType, upsert: false })`) — **no Uppy/TUS** (TUS's 6 MB chunk floor is incompatible with the bucket's 5 MiB per-file cap; see `architecture/image-upload-strategy`). Bounded worker pool, concurrency 3. `addFiles` validates each file via `validateImageFile` first — an invalid file lands directly in `status: 'error'` without ever calling Storage. `items` preserve `FileList`/selection order regardless of completion order (order is a property of the array, not of when a promise settles) — this is what lets `create_contenido_galeria` derive `orden` safely from `successfulPaths`. Per-item state machine `'pending' | 'uploading' | 'done' | 'error'`; a failed item does NOT abort the batch — other items keep uploading, and the failed one exposes `retry(objectName)`. `UploadItem.error` is typed `ErrorImagen | null`; `retry` is a no-op unless the item's error is `'upload_failed'` (a file rejected by `validateImageFile` is never re-queued, and keeps its reason). `remove(objectName)` drops an item and, if it was already `'done'`, best-effort purges the uploaded object from Storage (fire-and-forget). `canSubmit` is `items.length > 0 && items.every(i => i.status === 'done')` — the form gate a caller should use before calling `useCreateContenidoGaleria`/`useSetContenidoImagenes`. `objectName` shape is flat, one folder segment deep: `cma/<uuid>.<ext>` / `ic/<uuid>.<ext>`, deliberately with **no leading slash** — a leading slash produces an empty first `storage.foldername()` segment and silently breaks every RLS policy on this bucket.
- `UseUploadContenidoImagenesResult`, `UploadItem`, `UploadItemStatus` (types) — return shape / item shape / status union of `useUploadContenidoImagenes`.
- `validateImageFile(file: File)` — pure validator returning `{ ok: true } | { ok: false; error: 'formato_invalido' | 'tamano_excedido' }`. Allowed MIME: `image/jpeg`, `image/png`, `image/webp`, `image/avif`; `MAX_IMAGE_BYTES = 5 * 1024 * 1024`. Duplicates the `contenidos-imagenes` bucket's own `file_size_limit`/`allowed_mime_types` client-side so the admin gets an inline message instead of a raw Storage 413/415 — sibling of `validateMediaFile`, not a variant of it (image galleries have no "tipo" axis the way video/mantra do).
- `MAX_IMAGE_BYTES`, `ImageFileValidation` (const / type) — exports of `validateImageFile`.
- `describirErrorImagen(error: ErrorImagen)` — pure function returning `{ mensaje: string; reintentable: boolean }` for each reason a gallery image can land in `status: 'error'`. `ErrorImagen = 'formato_invalido' | 'tamano_excedido' | 'upload_failed'` (the two `validateImageFile` rejections + a failed Storage upload). Only `'upload_failed'` is `reintentable`: a rejected file would be rejected again. Copy lives in a `Map`, never an indexed object literal.
- `ErrorImagen`, `DescripcionErrorImagen` (types) — argument / return type of `describirErrorImagen`. Declared in `ContenidoTypes.ts`.
- `useUploadContenidoMedia(tipo: 'videos' | 'mantras' | 'egregores')` — hook returning `UseUploadContenidoMediaResult` (`{ uppy, state, recursoRef: string | null, duracionSeg: number | null, fileName: string | null, error: string | null, reset: () => void }`). Resumable (TUS, via Uppy) client→Storage upload of a single media file to the private `contenidos` bucket, in chunks of `UPLOAD_CHUNK_SIZE`. A finished upload is reconciled against the bucket (object exists with the expected size) before it is reported as a success (CON-002). `recursoRef` is what `useCreateContenido` receives.
- `UseUploadContenidoMediaResult`, `UseCreateContenidoGaleriaResult`, `UseSetContenidoImagenesResult` (types) — return shapes of `useUploadContenidoMedia`, `useCreateContenidoGaleria` and `useSetContenidoImagenes`.
- `validateMediaFile(file: File, tipo: 'videos' | 'mantras' | 'egregores')` — pure validator returning `MediaFileValidation` (`{ ok: true } | { ok: false; error: 'formato_invalido' | 'audio_tamano_excedido' }`). Only audio has a size ceiling: `MAX_AUDIO_BYTES = 100 * 1024 ** 2`.
- `MAX_AUDIO_BYTES`, `MediaFileValidation` (const / type) — exports of `validateMediaFile`.
- `UPLOAD_CHUNK_SIZE` (const) — `6 * 1024 * 1024`. The TUS chunk size of every resumable media upload, shared so the browser hook and the seed script cannot drift apart.
- `readMediaDuration(file: File): Promise<number | null>` — reads the duration (seconds) of a video/audio file from its metadata in the browser; resolves `null` if it cannot be read within the timeout. Runs alongside the upload.
- `contenidoLabel(c: Contenido): string` — display label of a contenido: its `titulo`, or `''` when it is `null`.

Internals (`utils/mapContenidoRow.ts` — its raw type `ContenidoRowRaw` IS exported, see barrel note above — `api/fetchAllContenido.ts`, `api/fetchContenidoById.ts`, `utils/validateMediaFile.ts`'s private constants, `utils/validateImageFile.ts`'s `ALLOWED_IMAGE_MIME`) are otherwise private to the folder and must not be imported from outside.

**`Contenido` shape:**

| Field         | Type                                                    | Meaning                                                         |
| ------------- | ------------------------------------------------------- | --------------------------------------------------------------- |
| `id`          | `string`                                                | Row id (uuid).                                                  |
| `tipo`        | `TIPO_CONTENIDO.VIDEO \| AUDIO \| EGREGOR \| CMA \| IC` | Discriminator.                                                  |
| `titulo`      | `string \| null`                                        | Display title. Nullable.                                        |
| `descripcion` | `string \| null`                                        | Long-form description / blurb. Nullable.                        |
| `contenido`   | `MediaContent { recursoRef, duracion }`                 | Media reference. `recursoRef`/`duracion` are `null` for CMA/IC. |
| `imagenes`    | `ReadonlyArray<ContenidoImagen { path, orden }>`        | Ordered gallery images. Always `[]` for VIDEO/AUDIO/EGREGOR.    |

All fields are `readonly`. Access `c.contenido.recursoRef` / `c.contenido.duracion` for media tipos; access `c.imagenes` for CMA/IC.

**`TIPO_CONTENIDO` values:** `VIDEO`, `AUDIO`, `EGREGOR`, `CMA`, `IC`, `TEXTO` (vestigial).

**DEC-0.6 note:** The entity `FraseMotivacional` was proposed and explicitly rejected by the user (contenidoPage/epic-0, task-0.2 gate); frases were instead modelled as `Contenido` with `tipo = TEXTO`. That entire manual ABM was later retired (frasesAutomaticas/epic-4) — see the note at the top of this section. Do **not** create `app/controllers/FraseMotivacional/`, and do **not** resurrect frase reads/writes under `Contenido/api/`.

**When to use.**

- Anywhere the domain talks about a unit of therapeutic content (video/audio/egregor media, or a CMA/IC image gallery) delivered in a weekly entrega. `useFetchAllContenido` covers the full catalog across all 5 tipos.
- Embedded as `ReadonlyArray<Contenido>` inside `EntregaSemanal` (see `Tratamiento`).
- Narrow `tipo` at the call site. For VIDEO/AUDIO/EGREGOR, read `contenido.recursoRef`/`contenido.duracion`. For CMA/IC, read `imagenes` (ordered by `orden`) — `contenido.recursoRef` is always `null` for galleries by design, not a bug to work around.
- Creating a gallery (CMA/IC) MUST go through `useCreateContenidoGaleria`, never `useCreateContenido` — the latter's `recurso_ref_vacio` guard is unconditional across all 5 tipos on purpose (see `sdd/new-media-types/spec-correction-01`).
- Do **not** use `Contenido` as a generic "asset" or "file" type — it is specifically the patient-facing therapeutic content piece.

## Diagnostico

**What it is.** The structured clinical assessment that anchors a `Tratamiento`, plus the two treatment-plan catalogs — `Modalidad` (the care modality that defines session count and nivel structure) and `Alfabeto` (the therapeutic alphabet applied to the treatment). Composed of one `Causa` (root cause), one `Algoritmo` (prescribed behavioural protocol), the set of `Bloqueos` the paciente presents, the full catalog of selectable `Modalidades`, and the full catalog of selectable `Alfabetos`. The therapist encodes the assessment once at the start of treatment; downstream content delivery + nivel evaluations key off it, and the wizard uses the catalogs for steps 2 and 3.

**Status.** Types + read hook for the full catalog. Extended in pacienteCreateFlow/task-0.4 to surface `Modalidad` and `Alfabeto` catalogs.

**Public API** (`app/controllers/Diagnostico/index.ts`):

- `Diagnostico` (type).
- `AllDiagnosticos` (type) — `{ causa: ReadonlyArray<Causa>, algoritmo: ReadonlyArray<Algoritmo>, bloqueos: ReadonlyArray<Bloqueo>, modalidades: ReadonlyArray<Modalidad>, alfabetos: ReadonlyArray<Alfabeto> }`. All nested types (`Causa`, `Bloqueo`, `Algoritmo`, `Modalidad`, `Alfabeto`) are **not** directly exported; consumers address them via indexed access (`AllDiagnosticos['causa'][number]`, `AllDiagnosticos['bloqueos'][number]`, `AllDiagnosticos['algoritmo'][number]`, `AllDiagnosticos['modalidades'][number]`, `AllDiagnosticos['alfabetos'][number]`).
- `useFetchAllDiagnosticos()` — hook returning `{ diagnosticos: AllDiagnosticos | null, isLoading: boolean, error: string | null }`. Runs five parallel queries on `causas`, `algoritmos`, `bloqueos`, `modalidades` (with `tipos_disco(nombre)` join), and `alfabetos`, all filtered by `activo = true`. `causa.etapas` and `algoritmo.etapas` are hydrated inline via Supabase relation select and sorted by `numeroEtapa`. First error across the five queries wins (precedence: causas → algoritmos → bloqueos → modalidades → alfabetos).
- `toAlfabetosCargados(filas: ReadonlyArray<FilaAlfabetoCargado>): ReadonlyArray<AlfabetoCargado>` (+ `FilaAlfabetoCargado` type `{ alfabetoId, nombre, orden, numero }`) — pure helper. Groups flat rows by alfabeto, dedupes and sorts the numbers ascending, orders the alfabetos by catalog `orden`.

Internals (`utils/mapCausaRow.ts`, `utils/mapAlgoritmoRow.ts`, `utils/mapBloqueoRow.ts`, `utils/mapModalidadRow.ts`, `utils/mapAlfabetoRow.ts`, `api/fetchAllDiagnosticos.ts`) are private to the folder and must not be imported from outside.

**`Diagnostico` fields:**

| Field       | Type                     | Meaning                                       |
| ----------- | ------------------------ | --------------------------------------------- |
| `causa`     | `Causa`                  | The root cause assigned to this treatment.    |
| `bloqueos`  | `ReadonlyArray<Bloqueo>` | All bloqueos identified for the paciente.     |
| `algoritmo` | `Algoritmo`              | The protocol prescribed to address the causa. |

**Nested shapes** (private to the entity but documented here for completeness):

- `Causa` — `id: string`, `codigo`, `nombre`, `definicion`, `emocionesEsperadas`, `activo`, `etapas: ReadonlyArray<CausaEtapa>`.
- `CausaEtapa` — `numeroEtapa`, `fraseEsperada` (the phrase the paciente is expected to express at that stage).
- `Bloqueo` — `id: string`, `codigo`, `nombre`, `descripcion`, `activo`.
- `Algoritmo` — `id: string`, `codigo`, `nombre`, `definicion`, `comportamiento`, `activo`, `etapas: ReadonlyArray<AlgoritmoEtapa>`.
- `AlgoritmoEtapa` — `numeroEtapa`, `fraseEsperada`.
- `Modalidad` — `id: string`, `codigo`, `nombre`, `tipoDiscoNombre: string | null` (flattened from `tipos_disco.nombre` join), `cantidadSesiones: number | null`, `cantidadNiveles: number`, `duracionMesesEstimada: number | null`, `activo: boolean`.
- `Alfabeto` — `id: string`, `codigo`, `nombre`, `descripcion: string | null`, `rangoMax: number` (highest selectable número), `orden: number` (catalog order 1..8; the catalog is fetched ordered by it), `activo: boolean`.
- `AlfabetoCargado` (type, exported) — `{ alfabetoId: string; nombre: string; numeros: ReadonlyArray<number> }`. Read-only view of an alfabeto loaded in a treatment: numeros sorted ascending and non-empty.

**When to use.**

- Embed it in a `Tratamiento`; do not pass `Causa` / `Algoritmo` / `Bloqueo` around individually as if they were top-level domain actors — they are catalog items the diagnosis composes.
- Use this type whenever a screen needs to display "what the terapeuta diagnosed for this paciente" as a single block (causa + bloqueos + algoritmo).
- When a consumer needs the full catalog of causas, algoritmos, and bloqueos for selection or display purposes (e.g. the diagnostic form), call `useFetchAllDiagnosticos`. When hydrating embedded diagnostico data inside a `Tratamiento`, note that `causa.etapas` and `algoritmo.etapas` are not populated by the `useFetchTratamientosByPaciente` read path — use `useFetchAllDiagnosticos` to get them.
- When a screen needs the full catalog of modalidades/alfabetos for selection (e.g. the patient creation wizard, plan-step), call `useFetchAllDiagnosticos`.

## Paciente

**What it is.** A person under treatment with the therapeutic team. The anchor of the rest of the domain — asignaciones, tratamientos, niveles, evaluaciones, and weekly entregas all hang off a paciente.

**Status.** Types + three read hooks (by terapeuta, by id, edit-hydration) + raw-row mappers + five mutation hooks (register, update identidad, update etapa diagnóstico, cerrar etapa, iniciar nueva etapa). Functional. The display mapper enriches the row with derived fields: `mesActual` / `mesesTotales` (mes de tratamiento, `ceil(semana / 4)`), `etapaOrdinal`, `evaluaciones`, `semanaGlobal` (semana del plan derivada de `fecha_inicio` de la etapa activa + hoy, capeada a `semanasTotales`), `semanasTotales` (`modalidades.cantidad_niveles * 4` de la etapa activa), `causaActual`, `ultimoScore`, `tendencia` (último vs penúltimo cronológico global), `proximaEvaluacion`, `inicioTratamiento` (estado del tratamiento más reciente). `tieneAlerta` sale siempre `false` del mapper y lo completa `marcarAlertas` con las alertas reales. `state` se resuelve desde `estados_paciente` (`ACTIVE` / `PAUSED` / `BAJA`).

**Public API** (`app/controllers/Paciente/index.ts`):

- `Paciente` (type).
- `Tendencia` (type) — `'up' | 'down' | 'flat'`.
- `PACIENTE_STATE` (enum) — `ACTIVE`, `PAUSED`, `BAJA`. Mirror of `estados_paciente` (`activo`, `pausado`, `baja_voluntaria`). Says whether the terapeuta still attends the paciente, **not** whether a tratamiento is running (term "Paciente activo" in `CONTEXT.md`).
- `EstadoInicioTratamiento` (type) — `'sin_iniciar' | 'en_curso' | 'finalizado' | 'sin_tratamiento'`. How the **most recent** tratamiento of the paciente stands (BETA-015). An open etapa wins over closed ones: `'sin_iniciar'` while it has no `fecha_inicio`, `'en_curso'` once it has one. With no open etapa: `'finalizado'` if there ever was one, `'sin_tratamiento'` if never. It is the type of `Paciente['inicioTratamiento']['estado']`; the container `InicioTratamiento` (`{ estado, fecha: string | null }`, `fecha` only set for `'en_curso'`) is declared in `PacienteTypes.ts` but not re-exported.
- `Paciente.tieneCuenta` / `Paciente.bienvenidaRecibida` (fields) — `pacientes.user_id !== null` and `pacientes.bienvenida_entregada_at !== null`, filled by `mapAsignacionToPaciente` (both selects read the two columns).
- `Paciente.algoritmoActual` / `Paciente.alfabetosActuales` (fields) — algoritmo (`{ nombre, definicion } | null`) and alfabetos (`ReadonlyArray<AlfabetoCargado>`, one entry per alfabeto) of the **active etapa**; `null` / `[]` without an active etapa. Filled by `mapAsignacionToPaciente`, which feeds `toAlfabetosCargados` from `etapa_alfabetos`.
- `AvisoDeInicio` (type) — `'bienvenida' | 'con_app' | 'ya_recibida'`. Which notice the "Iniciar tratamiento" dialog shows.
- `semanaActual(fechaInicio: string, hoy: Date): number` — pure helper, re-exported from the barrel (planBorrador/task-1.2). Semana de contenido (1-based) counted from `fechaInicio`, **without cap** (0/negative if the date is in the future, grows past the end of the plan). Consumers choose their cap: `mesActual`/`semanaGlobal` floor at 1 and cap at `semanasTotales`; `/asignar-contenido` uses it uncapped for `semanaEnCurso` to decide which weeks "ya pasó".
- `avisoDeInicio(paciente: Pick<Paciente, 'tieneCuenta' | 'bienvenidaRecibida'>): AvisoDeInicio` — pure helper; `ya_recibida` wins over `con_app`, else `bienvenida`.
- `marcarAlertas(pacientes: ReadonlyArray<Paciente>, alertas: ReadonlyArray<Alerta>): ReadonlyArray<Paciente>` — pure helper (BETA-007). Returns the same pacientes with `tieneAlerta` set from the real alertas of the engine (`Alerta.pacienteId`). The mapper cannot decide it (the aggregate is built from `asignaciones_paciente` and never sees `derive_alertas_activas()`), so every ViewModel that shows or filters by "con alerta" composes `useFetchPacientesByTerapeuta` + `useFetchAlertasTerapeuta` and passes both through this function.
- `UseFetchPacientesSinIniciarResult`, `UseFetchPacienteEditDataResult` (types) — return shapes of `useFetchPacientesSinIniciar` and `useFetchPacienteEditData`.
- `RegisterPacientePayload` (type) — the payload shape accepted by `useRegisterPaciente`.
- `RegisterPacienteResult` (type) — the shape returned by `useRegisterPaciente.submit()` and by the underlying fetcher: `{ pacienteId: string | null, error: string | null }`.
- `AlfabetoConNumero` (type) — `{ alfabetoId: string; numero: number | null }`. Pairs an alfabeto with its ordinal número within the etapa (nullable until the therapist sets it). Replaces the old "ids only" `alfabetoIds: string[]` shape everywhere alfabetos are read or written, so the TS payloads speak the same `jsonb` the `register_paciente` / `update_etapa_diagnostico` RPCs accept as `p_alfabetos`.
- `AlfabetoConNumeros` (type) — `{ alfabetoId: string; numeros: ReadonlyArray<number> }`. One alfabeto with all its selected números (replaces `AlfabetoConNumero` once the payloads migrate). Internal `utils/aplanarAlfabetos` / `utils/agruparAlfabetos` convert to/from the `{ alfabeto_id, numero }` row format; both are private to the entity.
- `PacienteEditData` (type) — flat editable projection for the edit form: `{ identidad, diagnostico, etapaId: string | null, etapaFresca: boolean, tieneCuenta: boolean }`. `identidad` = `PacienteEditIdentidad` `{ nombre, fechaNacimiento, email, telefono }`; `diagnostico` = `PacienteEditDiagnostico` `{ causaId, algoritmoId, modalidadId, bloqueoIds, alfabetos: ReadonlyArray<AlfabetoConNumero> }` (ids/alfabetos from the active etapa, `null`/empty when there is no active etapa). `etapaFresca` is `true` only when the active etapa has no progress (no nivel with `fecha_seguimiento_real`, no `nivel_evaluacion`) — same predicate the `update_etapa_diagnostico` RPC enforces server-side. `tieneCuenta` is `true` once the paciente activated the account (`pacientes.user_id` not null); with an account, `update_paciente_identidad` rejects an email change with `email_bloqueado_por_cuenta` (BETA-030), so the edit form disables the field.
- `PacienteEditIdentidad`, `PacienteEditDiagnostico` (types) — the two slices of `PacienteEditData`.
- `UpdatePacienteIdentidadPayload` (type) — payload for `useUpdatePacienteIdentidad`: `{ pacienteId, nombre, fechaNacimiento, email, telefono }`.
- `SetEtapaAlfabetosPayload` (type) — payload for `useSetEtapaAlfabetos`: `{ pacienteId, alfabetos: ReadonlyArray<AlfabetoConNumeros> }`. Result reuses `UpdatePacienteResult`.
- `UpdateEtapaDiagnosticoPayload` (type) — payload for `useUpdateEtapaDiagnostico`: `{ pacienteId, causaId, algoritmoId, modalidadId, bloqueoIds, alfabetos: ReadonlyArray<AlfabetoConNumero> }`.
- `UpdatePacienteResult` (type) — shape returned by all update/close mutations: `{ error: string | null }`.
- `EstadoCierre` (type) — `'finalizada' | 'abandonada'`. The closing state of an etapa; extracted as a named alias (code-review fix, `feat/nuevo-tratamiento`) so `CerrarEtapaPayload.estado` and `FinalizarTratamientoDialog`'s local `useState` share one source of truth instead of repeating the inline union.
- `CerrarEtapaPayload` (type) — payload for `useCerrarEtapa`: `{ pacienteId: string, estado: EstadoCierre, motivo: string | null }`.
- `IniciarNuevaEtapaPayload` (type) — payload for `useIniciarNuevaEtapa`: `{ pacienteId, causaId, algoritmoId, modalidadId, bloqueoIds: ReadonlyArray<string>, alfabetos: ReadonlyArray<AlfabetoConNumero> }`.
- `IniciarNuevaEtapaResult` (type) — shape returned by `useIniciarNuevaEtapa.submit()` and by the underlying fetcher: `{ etapaId: string | null, error: string | null }`.
- `useFetchPacientesByTerapeuta(terapeutaId: string | null)` — hook returning `{ pacientes: ReadonlyArray<Paciente>, isLoading: boolean, error: string | null, refresh: () => Promise<void> }`. `refresh()` re-fetches in background without flipping `isLoading` and keeps the previous list if the request fails (BETA-046: `/asignar-contenido` calls it after saving a plan, because completing the plan starts the treatment). Resolves to an empty list when `terapeutaId` is `null`. Filters by `terapeuta_id` and `fecha_hasta IS NULL` (only currently-active assignments).
- `useFetchPacientesSinIniciar(terapeutaId: string | null)` — hook returning `{ pacientes: ReadonlyArray<PacienteSinIniciar>, isLoading: boolean, error: string | null }`. Returns the terapeuta's active pacientes whose active etapa has **`fecha_inicio === null`** (didn't start yet — DEC-6c, Task 3.2; renamed from `useFetchPacientesSinContenido`, which used to ask "zero `entregas_plan` rows"). The new predicate fixes two divergences the old "zero entregas" proxy had: a paciente with a half-loaded plan (some entregas, still no `fecha_inicio`) now correctly appears; a paciente who already started and later had their plan deleted (zero entregas, `fecha_inicio` set) now correctly disappears. Dedicated dashboard fetch (does NOT go through `mapAsignacionToPaciente` nor the full `Paciente` aggregate, and does not query `entregas_plan` at all anymore). Resolves to an empty list when `terapeutaId` is `null`.
- `PacienteSinIniciar` (type) — minimal `{ id, nombre }` view for the "Sin iniciar" onboarding dashboard card (renamed from `PacienteSinContenido`); not the full aggregate.
- `useFetchPacienteById(pacienteId: string | null)` — hook returning `{ paciente: Paciente | null, isLoading: boolean, error: string | null }`. Resolves to `paciente = null` when `pacienteId` is `null` OR when no active asignacion exists for that paciente.
- `useRegisterPaciente()` — hook returning `{ submit: (payload: RegisterPacientePayload) => Promise<RegisterPacienteResult>, isSubmitting: boolean }`. Calls the `register_paciente` RPC atomically (paciente + asignacion + etapa + niveles + bloqueos + alfabetos). The `submit` function (1) uses `try/finally` so `isSubmitting` always resets even if the RPC throws, and (2) holds a `useRef` synchronous in-flight lock so two synchronous calls in the same React tick dedupe to a single RPC (the second caller receives the same in-flight promise). Consumers read the outcome — `pacienteId` and `error` — from the awaited `RegisterPacienteResult`, NOT from hook state (the hook does not expose either). The hook does not validate the payload — that responsibility belongs to the ViewModel. When you need to create a paciente with its initial diagnostico in one shot, use `useRegisterPaciente`.
- `useFetchPacienteEditData(pacienteId: string | null)` — hook returning `{ data: PacienteEditData | null, isLoading: boolean, error: string | null }`. Hydrates the edit form with the flat editable values of the paciente + its active etapa. Resolves to `data = null` when `pacienteId` is `null` OR when no active asignacion exists. Distinct from `useFetchPacienteById`, which returns the enriched display `Paciente` and drops the raw editable ids (no `algoritmoId`, no alfabetos).
- `useUpdatePacienteIdentidad()` — hook returning `{ submit: (payload: UpdatePacienteIdentidadPayload) => Promise<UpdatePacienteResult>, isSubmitting: boolean }`. Calls the `update_paciente_identidad` RPC (identidad + contacto, always editable, no progress gate). Same `try/finally` + `useRef` in-flight dedup contract as `useRegisterPaciente`. Read the outcome from the awaited `UpdatePacienteResult`.
- `useUpdateEtapaDiagnostico()` — hook returning `{ submit: (payload: UpdateEtapaDiagnosticoPayload) => Promise<UpdatePacienteResult>, isSubmitting: boolean }`. Calls the `update_etapa_diagnostico` RPC against the active etapa. The RPC enforces the freshness gate server-side (raises `etapa_con_progreso` if the etapa already started) and regenerates the niveles grid when the modalidad changes. Same dedup contract.
- `useSetEtapaAlfabetos()` — write hook returning `{ submit: (payload: SetEtapaAlfabetosPayload) => Promise<UpdatePacienteResult>, isSubmitting: boolean }`. Calls the `set_etapa_alfabetos` RPC, which replaces the alfabetos of the active etapa (one RPC entry per number) without touching the rest of the diagnosis. Errors: `numeros_invalidos`, `etapa_activa_no_encontrada`, `no_autorizado`. Same dedup contract.
- `dispararInvitacion(pacienteId: string): Promise<DispararInvitacionResult>` — bare fetcher (no hook wrapper: lo llama `iniciarTratamiento`, no un componente). Invoca la Edge Function `paciente-invitacion`, que manda el mensaje de **bienvenida** por WhatsApp — desde activacionPorTelefono ya no emite OTPs (ADR-0001/0005). `DispararInvitacionResult` = `{ ok: boolean; enviadas: number | null; error: string | null }`. `enviadas` es la cuenta que devuelve el body de la EF (`{ ok, enviadas }`, activacionPorTelefono/ACT-003): `1` salió la bienvenida, `0` no hacía falta (ya la recibió / ya tiene cuenta / baja voluntaria — las tres guardas de `decidirInvitacion`, y el caso normal al volver a guardar un plan completo), `null` no se pudo saber (invocación fallida o body sin el campo). Distinguir `1` de `0` es lo único que deja avisarle al terapeuta si salió un WhatsApp sin mentirle cuando no salió ninguno; `iniciarTratamiento` lo traduce a su `EstadoBienvenida`.
- `cerrarEtapa(payload: CerrarEtapaPayload)` — bare fetcher (not just wrapped by the hook, exported directly per the `dispararInvitacion` precedent) that calls the `cerrar_etapa` RPC (`p_paciente_id`, `p_estado`, `p_motivo`) and returns `UpdatePacienteResult`.
- `useCerrarEtapa()` — hook returning `{ submit: (payload: CerrarEtapaPayload) => Promise<UpdatePacienteResult>, isSubmitting: boolean }`. Wraps `cerrarEtapa` via `useSubmitMutation` — same `try/finally` + `useRef` in-flight dedup contract as the other mutation hooks. Closes the active etapa (`estado: EstadoCierre`, optional `motivo`); server-side validation of the closing rules lives in the `cerrar_etapa` RPC (Task 1.1), not in this hook.
- `iniciarTratamiento(payload: IniciarTratamientoPayload): Promise<IniciarTratamientoResult>` / `useIniciarTratamiento()` — (planBorrador, DEC-05: vive en Paciente junto a `cerrarEtapa`/`dispararInvitacion`.) Llama el RPC `iniciar_tratamiento(p_etapa_id, p_entregas_plan)`; `payload = { etapaId, semanas: ReadonlyArray<SemanaContenido> | null }` (`null` = no toca el plan; si no, se serializa con `serializeEntregasPlan`). Mapea `error.message` a `ErrorDeInicio` (`'etapa_cerrada' | 'paciente_dado_de_baja' | 'semana_pasada' | 'desconocido'`). Si `iniciado` es `true` dispara `dispararInvitacion(pacienteId)` y traduce `enviadas` a `EstadoBienvenida` (`1` → `'enviada'`, `0` → `'innecesaria'`, `null` → `'desconocida'`, fallo de invocación → `'fallida'` con `ok: true`). Resultado `{ ok, error, iniciado, bienvenida }`. El hook envuelve el fetcher con `useSubmitMutation`.
- `useReenviarBienvenida()` — (planBorrador) hook sobre `dispararInvitacion` que devuelve `{ reenviar: (pacienteId: string) => Promise<ResultadoReenvio>, isSending: boolean }`, con guard de re-entrada (`useRef`: llamadas concurrentes comparten la promesa en vuelo). `ResultadoReenvio` = `'enviada' | 'innecesaria' | 'error'`: `enviadas: 1` → `enviada`; `0` → `innecesaria` (el paciente ya tiene la app o ya la recibió); invocación fallida o `enviadas: null` → `error`.
- `isBienvenidaPendiente(paciente: Pick<Paciente, 'sinIniciar' | 'etapaActivaId' | 'tieneCuenta' | 'state' | 'bienvenidaRecibida'>): boolean` — pure helper. `etapaActivaId !== null && !sinIniciar && !tieneCuenta && state !== PACIENTE_STATE.BAJA && !bienvenidaRecibida`: el tratamiento arrancó y la bienvenida nunca se entregó.
- `hasEtapaActiva(paciente: Paciente): boolean` — pure helper (no fetch). Returns `paciente.etapaActivaId !== null` (Task 0.2, fix for H1 — superseded DEC-04's `fechaInicioEtapaActiva !== null`, which stopped working once `fecha_inicio` became nullable). `true` iff the paciente currently has an open etapa, **started or not**; `false` only when there is no open etapa at all (never started, or last etapa was closed). Unlike `etapaOrdinal`/`mesActual` (which stay internal to the mapper), this helper is exported directly from the barrel because it is meant to be called by UI components (e.g. the paciente detail header) that need to gate "finalizar tratamiento" / "nuevo tratamiento" actions without re-deriving the check inline.
- `useIniciarNuevaEtapa()` — hook returning `{ submit: (payload: IniciarNuevaEtapaPayload) => Promise<IniciarNuevaEtapaResult>, isSubmitting: boolean }`. Calls the `iniciar_nueva_etapa` RPC (`p_paciente_id`, `p_causa_id`, `p_algoritmo_id`, `p_modalidad_id`, `p_bloqueo_ids`, `p_alfabetos`), which atomically opens a new etapa (+ niveles + bloqueos + alfabetos) for a paciente whose previous etapa was already closed (Task 2.1). Same `try/finally` + `useRef` in-flight dedup contract as the other mutation hooks (via `useSubmitMutation`). Read the outcome — `etapaId` and `error` — from the awaited `IniciarNuevaEtapaResult`. Use `hasEtapaActiva` to gate when this action should be offered (only when it returns `false`).
- `TelefonoEnOtraFichaResult` (type) — `{ enOtraFicha: boolean, error: string | null }`. Shape returned by `useCheckTelefonoEnOtraFicha().check()`.
- `useCheckTelefonoEnOtraFicha()` — hook returning `{ check: (telefono: string, excluirPacienteId: string | null) => Promise<TelefonoEnOtraFichaResult> }` (activacionPorTelefono Task 2.4). Calls the `telefono_en_otra_ficha` RPC (`p_telefono`, `p_excluir_paciente_id`); an RPC error collapses to `{ enOtraFicha: false, error: error.message }` so a failed check never fabricates a false-positive warning. Deliberately **not** built on `useSubmitMutation` — its synchronous in-flight lock would drop a second check for a different phone fired while the first is still resolving. `check` is a stable (`useCallback`) reference across renders. Non-blocking UX check (the identidad ayuda/aviso in the nuevo/editar wizards) — never gates submit; the DB's own `telefono_invalido` / uniqueness rules remain the source of truth.
- `FichaPorEmail` (type) — `{ id: string, nombre: string, dadoDeBaja: boolean, accesible: boolean }`. The ficha that already holds an email, as RLS lets the caller see it (ADR 0010). `dadoDeBaja` = its estado is `baja_voluntaria`; `accesible` = the caller sees an open asignación (`fecha_hasta IS NULL`), i.e. `/pacientes/[id]` opens for them — same criterion as `useFetchPacienteById`. For a terapeuta the embed only carries their own asignaciones, so `accesible: false` means "ex-paciente": the duplicate-email notice does not name that ficha (BETA-034).
- `BuscarFichaPorEmailResult` (type) — `{ ficha: FichaPorEmail | null, error: string | null }`. Shape returned by `useBuscarFichaPorEmail().buscar()`.
- `useBuscarFichaPorEmail()` — hook returning `{ buscar: (email: string, excluirPacienteId: string | null) => Promise<BuscarFichaPorEmailResult> }` (pulidoBeta BETA-003, ADR 0010). Reads `pacientes` (`id, nombre, estados_paciente ( codigo ), asignaciones_paciente ( fecha_hasta )`) by **exact** email (no case normalization — must stay co-extensive with the unique index `pacientes_email_key`), optionally excluding the ficha being edited. **There is no privacy rule in the hook: RLS decides.** A returned `ficha` means it is the caller's own (or the caller is admin); `null` means "another terapeuta's or nonexistent", indistinguishable on purpose — never name a paciente from a `null`. A query error collapses to `{ ficha: null, error }`, i.e. the generic aviso. Imperative lookup, not a mount-time fetch: call it only on the error path, after a mutation returned `email_duplicado`. `buscar` is a stable (`useCallback`) reference.
- **Error code `email_duplicado`** — `useRegisterPaciente`, `useUpdatePacienteIdentidad` and `useUpdateEtapaDiagnostico` surface it in `error` when the RPC fails with SQLSTATE `23505` naming `pacientes_email_key` (private `utils/toRpcErrorCode.ts`); every other error still surfaces its raw `message`. Copy lives in `lib/identidadMessages.ts` (`mapIdentidadRpcError`, `resolverEmailDuplicado`).

Internals (`api/fetchPacientesByTerapeuta.ts`, `api/fetchPacienteById.ts`, `api/useFetchPacienteById.ts`, `api/fetchPacienteEditData.ts`, `api/updatePacienteIdentidad.ts`, `api/updateEtapaDiagnostico.ts`, `api/callUpdateRpc.ts`, `api/iniciarNuevaEtapa.ts`, `api/checkTelefonoEnOtraFicha.ts`, `utils/mapAsignacionToPaciente.ts`, `utils/mapAsignacionToPacienteEditData.ts` with its private `PacienteEditRaw` row type, the raw `AsignacionRaw` row type) are private to the folder and must not be imported from outside. `cerrarEtapa`/`useCerrarEtapa` are the exception — the fetcher is re-exported directly (see above), not just its hook wrapper. The display mapper accepts an optional `today: Date` parameter for deterministic testing — production callers omit it and the mapper falls back to `new Date()`.

**When to use.**

- Any feature that needs to list, search, or display a paciente from the perspective of the logged-in terapeuta or admin. Compose `useFetchPacientesByTerapeuta` with `useCurrentUserId` inside the ViewModel — never inline a Supabase query against `pacientes` / `asignaciones_paciente`.
- To fetch a single paciente (e.g. a detail page), use `useFetchPacienteById`.
- Example consumer: `app/pacientes/controllers/usePacientesViewModel.ts`.
- For any new write paths (create, update, assign), **add a new file under `api/`** in this folder rather than fetching from a ViewModel or page-local controller (Rule 5 of `controllers-architecture.md`).

## Terapeuta

**What it is.** A member of the therapeutic team — the human actor logged into this web console. 1:1 with a `Profile` whose `role` is pinned to `ROLE.TERAPEUTA`.

**Status.** Types + three read hooks (by id, all, dashboard rollup) + raw-row mappers + mutation hooks. Functional. `useFetchAllTerapeutas` and `useFetchTerapeutasDashboard` go via the `list_terapeutas` RPC (extended additively with `score_promedio`/`alertas_activas` for the dashboard, and `sin_iniciar` for the `/terapeutas` admin table — DEC-12, `feat/inicio-tratamiento` post-implementation). `useFetchTerapeutaById` now uses the `get_terapeuta` RPC (migrated in Epic 3, Task 3.4) — `email` and `pacientesActivos` are fully populated.

**Public API** (`app/controllers/Terapeuta/index.ts`):

- `Terapeuta` (type) — `id` is `string` (uuid).
- `TERAPEUTA_STATE` (enum).
- `useFetchTerapeutaById(terapeutaId: string | null)` — hook returning `{ terapeuta: Terapeuta | null, isLoading: boolean, error: string | null, refresh: () => void }`. Calls `get_terapeuta` RPC via `supabase.rpc('get_terapeuta', { p_terapeuta_id })`. Resolves to `terapeuta = null` when `terapeutaId` is `null` or when the RPC returns an empty set. `email` and `pacientesActivos` are fully populated. `refresh()` triggers a re-fetch imperatively — call it after a mutation to update the detail without a full page reload.
- `useFetchAllTerapeutas()` — hook returning `{ terapeutas: ReadonlyArray<Terapeuta>, isLoading: boolean, error: string | null, refresh: () => void }`. Calls the `list_terapeutas` RPC via `supabase.rpc('list_terapeutas')`. Returns all terapeutas the RPC exposes (admin only — non-admin callers receive the `no_autorizado` error surfaced via the `error` field). `email` and `pacientesActivos` are fully populated. `refresh()` triggers a re-fetch imperatively — call it after a mutation to update the list without a full page reload.
- `useFetchTerapeutasDashboard()` — hook returning `{ terapeutas: ReadonlyArray<TerapeutaRollup>, isLoading: boolean, error: string | null, refresh: () => void }`. Calls the **same** `list_terapeutas` RPC, but maps the additive columns `score_promedio` / `alertas_activas` into a lean `TerapeutaRollup` (the old `useFetchAllTerapeutas` mapper ignores them — extensión aditiva, no rompe el read path existente). Admin only. Built for the admin dashboard rollup ("carga y salud por terapeuta").
- `TerapeutaRollup` (type) — fila lean del rollup del dashboard admin: `id`, `nombre`, `estado` (`TERAPEUTA_STATE`), `pacientesActivos`, `scorePromedio` (`number | null`), `alertasActivas` (`number | null`). Las métricas Tier B (`scorePromedio`/`alertasActivas`) son `null` cuando el caseload activo del terapeuta no tiene evaluaciones (distinto de `0`).
- `resolveDesactivarErrorMessage(codigo, count)` — función pura: traduce el código de error de `useDeactivateTerapeuta().mutate` (`result.error`, `result.errorCount`) al mensaje para el admin. `'tiene_pacientes_activos'` → "Este terapeuta tiene N paciente(s) a cargo…" con singular/plural real; `'no_puede_autodesactivarse'` → "No podés desactivar tu propia cuenta."; cualquier otro código (o ninguno) → mensaje genérico. La usan los ViewModels de `/terapeutas` y `/terapeutas/[id]`.

Internals (`utils/mapTerapeutaRow.ts` with its private `TerapeutaRowRaw` type, `utils/mapTerapeutaRpcRow.ts` with its private `TerapeutaRpcRow` type, `utils/mapTerapeutaDashboardRow.ts` with its private `TerapeutaDashboardRow` type, `api/fetchTerapeutaById.ts`, `api/fetchAllTerapeutas.ts`, `api/fetchTerapeutasDashboard.ts`) are private to the folder and must not be imported from outside.

**Mutation hooks (invitation lifecycle):**

- `useInviteTerapeuta()` — returns `{ mutate, isLoading, error }` where `mutate({ nombre, email })` calls the `terapeuta-invitations` Edge Function with `action: 'invite'`. On success returns `{ ok: true, terapeutaId: string }`; on any error returns `{ ok: false }` and surfaces the error code in `error`. Known `data.error` codes: `'email_duplicado'`, `'validacion_invalida'`, `'no_autorizado'`, `'invite_failed'`.
- `useResendInvitation()` — returns `{ mutate, isLoading, error }` where `mutate({ terapeutaId })` calls the Edge Function with `action: 'resend'`. Returns `{ ok: boolean }`. Known `data.error` codes: `'estado_invalido'`, `'no_autorizado'`, `'resend_failed'`.
- `useRevokeInvitation()` — returns `{ mutate, isLoading, error }` where `mutate({ terapeutaId })` calls the Edge Function with `action: 'revoke'`. Returns `{ ok: boolean }`. Known `data.error` codes: `'estado_invalido'`, `'no_autorizado'`, `'delete_failed'`.

**Mutation hooks (profile update + activation lifecycle):**

- `useUpdateTerapeuta()` — returns `{ mutate, isLoading, error }` where `mutate({ terapeutaId, nombre, telefono })` calls `supabase.rpc('update_terapeuta', ...)` directly (no Edge Function needed — no service-role required). On success returns `{ ok: true, terapeuta: Terapeuta }`; on error returns `{ ok: false }`. Known error codes: `'nombre_vacio'` (nombre is blank); any other RPC error maps to `'update_failed'`.
- `useDeactivateTerapeuta()` — returns `{ mutate, isLoading, error, errorCount }` where `mutate({ terapeutaId, motivo })` calls the `terapeuta-invitations` Edge Function with `action: 'deactivate'`. Returns `{ ok: boolean }`. Known error codes: `'tiene_pacientes_activos'` (paired with `errorCount: number` — the count of active patients); `'no_puede_autodesactivarse'`; `'motivo_requerido'`; `'deactivate_failed'` (generic). `errorCount` is `number | null` — non-null only when `error === 'tiene_pacientes_activos'`.
- `useReactivateTerapeuta()` — returns `{ mutate, isLoading, error }` where `mutate({ terapeutaId })` calls the Edge Function with `action: 'reactivate'`. Returns `{ ok: boolean }`. Known error codes: `'reactivate_failed'`.
- `UseFetchTerapeutasDashboardResult`, `UseInviteTerapeutaResult`, `UseResendInvitationResult`, `UseRevokeInvitationResult`, `UseUpdateTerapeutaResult`, `UseDeactivateTerapeutaResult`, `UseReactivateTerapeutaResult` (types) — return shapes of the hooks of the same name.

All mutation hooks are client-only (`'use client'`). The `error` field is `string | null` — it holds the raw code string from `data.error` or `invokeError.message`. The ViewModel that consumes these hooks is responsible for mapping error codes to user-facing copy.

**When to use.**

- Any admin-facing flow that lists, manages, or assigns terapeutas. Use `Terapeuta` (not raw `Profile`) when the role context matters — the embedded `profile` carries the personal data, while the outer shape carries the team-membership semantics.
- Use `email` (the flat field on `Terapeuta`) rather than `profile.email` — once the Epic 1 RPC lands it will be the populated source of truth.
- For the currently logged-in user's identity, do **not** reach for `Terapeuta` — use `useCurrentUserId` from `Auth`. `Terapeuta` is about the actor as a domain object, not about the auth session.
- For invitation flows, reach for the mutation hooks above rather than calling `supabase.functions.invoke` directly from a ViewModel.

## Tratamiento

**What it is.** The active treatment plan a terapeuta builds for a paciente. The central aggregate of the product's value proposition: "the terapeuta loads the plan once and the system delivers content, follow-ups, evaluations and reminders automatically for months." Composes the diagnosis, the monthly niveles of follow-up, and the weekly content deliveries.

**Status.** Types + three read hooks (by paciente, evaluaciones del tratamiento activo, historia completa del paciente) + raw-row mappers. Shell hydration: `diagnostico` is fully populated; `niveles` and `entregasSemanales` are returned as empty arrays by `useFetchTratamientosByPaciente`.

**Public API** (`app/controllers/Tratamiento/index.ts`):

- `Tratamiento` (type).
- `TRATAMIENTO_STATE` (enum).
- `EtapaStatus` (enum) — `PENDIENTE`, `EN_CURSO`, `FINALIZADA`, `ABANDONADA`. Status of a single treatment stage in the historia read path. `PENDIENTE` (added in `inicioTratamiento/task-4.1`) is the code for an etapa created but not yet started (`fecha_inicio null`, `estados_etapa.codigo = 'pendiente'`) — `resolveStatus` no longer falls back to `EN_CURSO` for this code.
- `isEtapaCerrada(status: EtapaStatus): boolean` — true for `FINALIZADA`/`ABANDONADA`, false for `EN_CURSO`/`PENDIENTE`. The single predicate for "is this stage closed"; use it instead of re-deriving the `status === FINALIZADA || status === ABANDONADA` check inline (it broke twice, silently, when `PENDIENTE` was added).
- `EtapaHistoria` (type) — the enriched projection of one `etapas_tratamiento` row for the Historia tab. Fields: `id`, `status: EtapaStatus`, `fechaInicio: string | null` (nullable since `inicioTratamiento/task-4.1` — `null` for an etapa that never started, whether still open (`PENDIENTE`) or closed without ever starting (`FINALIZADA`/`ABANDONADA` with `fecha_inicio null`, DEC-10/DEC-11's escape hatch); consumers must null-check before formatting a date), `fechaFin`, `diagnostico: Diagnostico`, `modalidad: { nombre, cantidadNiveles, duracionMesesEstimada } | null`, `responsables: ReadonlyArray<TerapeutaResponsable>`, `eventos: ReadonlyArray<EventoEvolucion>`, `duracionMeses: number | null` (`null`, never `NaN`, when `fechaInicio` is `null`), `deltaScoreEtapa: { primero, ultimo } | null`, `motivoCierre: string | null`, `proximaEvaluacion: string | null`, `alfabetos: ReadonlyArray<AlfabetoCargado>` (alfabetos cargados en ESA etapa, one per alfabeto with sorted numbers, built via `toAlfabetosCargados` from the `etapa_alfabetos(numero, alfabetos(id, nombre, orden))` embed). Internally, `mapEtapasToHistoria` anchors every time-window calculation (responsables overlap, cambio_terapeuta filtering, output sort) on `etapaSortKey(fechaInicio, createdAt)` (`app/utils/etapaSortKey.ts` — `coalesce(fecha_inicio, created_at::date)`, the single shared helper also used by `Paciente`'s `etapaOrdinal.ts`, `mapAsignacionToPaciente.ts` and `mapAsignacionToPacienteEditData.ts`, and mirrored in `65_alertas.sql`/`62_rpc_admin.sql`) — so an unstarted etapa still resolves its responsables and keeps its correct chronological position instead of silently degrading to `[]`/wrong order.
- `TerapeutaResponsable` (type) — `{ terapeutaId: string, nombre: string }`. A terapeuta whose assignment overlapped a given etapa.
- `EventoEvolucion` (type) — discriminated union: `{ tipo: 'nivel', fecha, numeroNivel, score: number | null, deltaScore: number | null }` | `{ tipo: 'cambio_terapeuta', fecha, de, a, motivo: string | null }`. One event in the timeline of an etapa.
- `FraseDerivada` (type) — `{ readonly orden: number; readonly origen: 'causa' | 'algoritmo'; readonly texto: string }`. One auto-derived motivational phrase slot of a week (frasesAutomaticas/epic-0, Task 0.4). Embedded as `ReadonlyArray<FraseDerivada>` inside `FrasesPorSemana` (see below) — the **only** place it is embedded since frasesAutomaticas/FRA-005 retired the sibling `EntregaSemanal.frases` field (see the note on `EntregaSemanal` below).
- `FrasesPorSemana` (type) — `Readonly<Record<number, ReadonlyArray<FraseDerivada>>>` (frasesAutomaticas/epic-1, Task 1.2). Frases derived from the etapa's causa/algoritmo, keyed by número de semana, for **every** week of the etapa — independent of whether that week has any `entregas_plan` row. This is the **single source of truth** for "this week's 3 frases" (frasesAutomaticas/FRA-005) — index it directly, there is no other path to the derived phrases.
- `SlotKey` (type) — `'meditacion' | 'mantra' | 'egregor' | 'cma' | 'ic'` (widened 2→5 in `new-media-types/PR4`). The 5 fillable/persistable columns of the weekly plan grid — what gets written to `entregas_plan`. Must mirror `public.etapa_plan_completo`'s orden filter and `public.set_entregas_plan`'s tipo-per-orden validation (DEC-8, `71_rpcs_pacientes.sql`) EXACTLY.
- `ColumnKey` (type) — `SlotKey | 'frases'` (frasesAutomaticas/FRA-006). The 6 grid COLUMNS: the 5 persistable slots plus the read-only, automatic `'frases'` column. Every `SlotKey` is a `ColumnKey`, but `'frases'` is never persisted through this module.
- `SLOT_DEFINITIONS` (const, added `new-media-types/PR4`) — `ReadonlyArray<{ key: SlotKey; orden: number; source: TIPO_CONTENIDO }>`, `[{meditacion,1,VIDEO},{mantra,2,AUDIO},{egregor,3,EGREGOR},{cma,4,CMA},{ic,5,IC}]`. The single source of truth for orden↔tipo↔slot, pinned by `slotDefinitions.test.ts` against the SQL mirror in `71_rpcs_pacientes.sql`. Consumed by `useAsignarContenidoViewModel` to build `contenidosBySlot` (filter the catalog by each slot's `source` tipo) and by `serializeEntregasPlan`.
- `SLOT_KEYS` (const) — `ReadonlyArray<SlotKey>`, `['meditacion', 'mantra', 'egregor', 'cma', 'ic']` in that order (derived from `SLOT_DEFINITIONS`). Drives completeness checks (`isSemanaCompleta`/`isSlotMissing` in `app/asignar-contenido/controllers/utils/semanaCompleteness.ts`) and the slot-header iteration in `SemanaRow`/`PlanEnviosCard`.
- `SEMANA_GRID_TEMPLATE` (const) — the shared CSS grid `gridTemplateColumns` string for the weekly plan table, so the header (`PlanEnviosCard`) and each data row (`SemanaRow`) — independent grids — stay column-aligned. 7 tracks since `new-media-types/PR4` (`'96px repeat(5, minmax(0, 1fr)) minmax(0, 1.2fr)'`).
- `SemanaContenido` (type) — `{ readonly semana: number; readonly meditacion: string | null; readonly mantra: string | null; readonly egregor: string | null; readonly cma: string | null; readonly ic: string | null }`. The input shape for `serializeEntregasPlan`; represents one week of the content plan as chosen by the terapeuta. The `frase` field was retired in frasesAutomaticas/epic-1, Task 1.2 — frases are read-only/derived now (see `FrasesPorSemana`), never part of the editable draft.
- `EntregaPlanInsertRow` (type) — `{ readonly semana: number; readonly orden: number; readonly contenido_id?: string }`. The write/insert shape for one row sent to the `set_entregas_plan` RPC — one row per persistable slot (meditacion/mantra/egregor/cma/ic; frases are never persisted through this path). (Distinct from the raw read shape `EntregaPlanRawRow` in `mapEtapaToTratamientoConEntregas.ts`, which carries `dia_offset` + nested join objects.)
- `serializeEntregasPlan(semanas: ReadonlyArray<SemanaContenido>): EntregaPlanInsertRow[]` — converts the terapeuta's weekly content grid to the flat rows the RPC expects. One row per non-null slot. Null slots produce no row. Orden is driven by `SLOT_DEFINITIONS` (meditacion=1, mantra=2, egregor=3, cma=4, ic=5 — 5 persistable slots since `new-media-types/PR4`).
- `useFetchTratamientosByPaciente(pacienteId: string | null)` — hook returning `{ tratamientos: ReadonlyArray<Tratamiento>, isLoading: boolean, error: string | null }`. Joins `etapas_tratamiento + estados_etapa + causas + algoritmos + etapa_bloqueos -> bloqueos`. Rows missing a `causa` or `algoritmo` join (FK orphan / RLS-hidden) are skipped — that is the only skip condition. An etapa with `fecha_inicio null` (created but not yet started, `inicioTratamiento`) is **not** skipped: it IS returned as a `Tratamiento`, with `fechaInicio: null` — it is precisely the one that needs content loaded so it can start (INI-001). `Tratamiento.fechaInicio` is therefore `string | null` (see the field table below). Currently unconsumed by any page. `niveles` and `entregasSemanales` are returned as `[]`; consumers must not rely on them being populated yet. `causa.etapas` and `algoritmo.etapas` are not hydrated by this read path — consumers needing them should call `useFetchAllDiagnosticos` from `Diagnostico`.
- `useSetEntregasPlan()` — mutation hook returning `{ submit: (etapaId: string, semanas: ReadonlyArray<SemanaContenido>) => Promise<SetEntregasPlanResult>, isSubmitting: boolean, error: string | null }`. `SetEntregasPlanResult` = `{ ok: boolean; error: string | null; semanaPasada: number | null }`. Desde planBorrador **solo guarda el borrador**: nunca arranca el tratamiento ni invoca `paciente-invitacion` (eso es `useIniciarTratamiento` en Paciente). `semanaPasada` sale del `details` del error `semana_pasada` (`null` en cualquier otro caso). Calls `serializeEntregasPlan(semanas)` then `supabase.rpc('set_entregas_plan', { p_etapa_id, p_entregas_plan })`. On RPC error, maps `error.message` to the `error` state and returns `{ ok: false, error, semanaPasada }`. Does not navigate or show toasts — that is the ViewModel's responsibility (Rule 5).
- `semanasConContenido(plan: ReadonlyArray<SemanaContenido>): number` — util exportada: cantidad de semanas con al menos un casillero no nulo (compartida por Asignar contenido y la ficha).
- `mapEntregasToSemanas(entregasSemanales: ReadonlyArray<EntregaSemanal>, semanasTotales: number): ReadonlyArray<SemanaContenido>` — pure inverse of `serializeEntregasPlan`: builds the editable grid (one `SemanaContenido` per week, length `semanasTotales`) from the entregas of a tratamiento; slots with no entrega stay `null`.
- `UseSetEntregasPlanResult`, `UseFetchEstructuraPacienteResult` (types) — return shapes of `useSetEntregasPlan` and `useFetchEstructuraPaciente`.
- `useFetchPlanContenidoDelTratamientoActivo(pacienteId: string | null)` — hook returning `{ tratamiento: Tratamiento | null, semanasTotales: number | null, cantidadNiveles: number | null, frasesPorSemana: FrasesPorSemana, isLoading: boolean, error: string | null, refresh: () => void }`. `refresh()` re-fetches the same paciente in background without flipping `isLoading` (BETA-046; only a paciente change shows the loading state). Fetches the active `etapas_tratamiento` for the paciente with nested `entregas_semanales` and their `contenido` join, fully hydrating `entregasSemanales`. `tratamiento.id` is the `etapaId` needed for `useSetEntregasPlan`. Resolves to `{ tratamiento: null, semanasTotales: null, cantidadNiveles: null, frasesPorSemana: {} }` when `pacienteId` is `null` or no active etapa exists. **frasesAutomaticas/epic-0, Task 0.4:** the underlying fetcher (`fetchPlanContenidoDelTratamientoActivo`) additionally calls the `get_frases_del_tratamiento_activo` RPC **in parallel** (`Promise.all`) with the plan query — they are independent (DEC-0-6). The `frase:frases_motivacionales` join on `entregas_plan` was **retired** in this same task (frases are no longer a manually-assigned content item). If the frases RPC errors or returns no data, the fetcher degrades silently: the plan resolves normally with `frasesPorSemana: {}`, `error` stays `null` — a catalog/RPC problem must never block loading video/mantra, which is what unblocks the treatment. **frasesAutomaticas/epic-1, Task 1.2:** the RPC rows are exposed directly as `frasesPorSemana` (keyed by número de semana, for every week of the etapa). **frasesAutomaticas/FRA-005:** the sibling `EntregaSemanal.frases` field this section used to also mention was deleted — it duplicated the same `?? []` merge as the ViewModels, disagreed with `frasesPorSemana` on which weeks it covered, and had no production reader. `frasesPorSemana` is the only way to read a week's derived phrases.

Resolves to `tratamiento = null` when `pacienteId` is `null` or no active etapa exists. Supports cancellation via an `AbortController`-style flag on re-render and exposes `refresh()` for imperative re-fetching after mutations. Use this hook — not `useFetchTratamientosByPaciente` — whenever the screen needs the full list of niveles and their evaluaciones for the active tratamiento (e.g. the evaluaciones tab of a paciente detail page).
- `useFetchHistoriaDelPaciente(pacienteId: string | null)` — hook returning `UseFetchHistoriaDelPacienteResult` (`{ etapas: ReadonlyArray<EtapaHistoria>, centros: ReadonlyArray<CentroEnergetico>, isLoading: boolean, error: string | null, refresh: () => void }`). Fetches ALL `etapas_tratamiento` rows for the paciente (not just the active one — including `fecha_inicio null`, `created_at` per `inicioTratamiento/task-4.1`) plus `asignaciones_paciente`, plus (medir-chakras/PR2) the `centros_energeticos` catalog, in three parallel queries, then derives the full clinical history via `mapEtapasToHistoria`. The etapas query embeds `mediciones_estructura(...)` (+ `profiles(nombre)` for the author, + `medicion_valores(centro_id, valor)`), which `mapEtapasToHistoria` projects into each `EtapaHistoria.mediciones` and into `medicion` timeline events. `centros` is the catalog read separately (RLS `using (true)`) so the Historia matrix (PR5) gets one stable row order shared across every etapa of a chapter — embedding it per-medición would let two etapas disagree. RLS governs data visibility: a terapeuta sees only their own assignment row + etapas for the currently-assigned patient; an admin sees all. - `UseFetchHistoriaDelPacienteResult` (type) — the return shape of `useFetchHistoriaDelPaciente`.

Anything about a week's derived phrases goes through `FrasesPorSemana`/`frasesPorSemana`, never through `EntregaSemanal`.

Internals (`utils/mapEtapaToTratamiento.ts`, `utils/slotDefinitions.ts` with its private `SlotSource`/`SlotDefinition` types — `SLOT_DEFINITIONS` itself is public since `new-media-types/PR4` (see above); `SlotKey` itself is public, defined in `TratamientoTypes.ts` — see above), `utils/mapEtapaToTratamientoConEntregas.ts` with its private `EntregaPlanRawRow` and `FrasesPorSemanaRawRow` (the `{ semana, frases }` raw grouping returned by `get_frases_del_tratamiento_activo`, whose inner items reuse the public `FraseDerivada` shape as-is) types, `api/fetchTratamientosByPaciente.ts`, `api/fetchEvaluacionesDelTratamientoActivo.ts`, `api/fetchPlanContenidoDelTratamientoActivo.ts`, and the raw row types defined within) are private to the folder and must not be imported from outside.

### medir-chakras / PR2 additions — mediciones de estructura de centros energéticos

Nested types on the existing `Tratamiento` entity (same precedent as `Nivel`/`Evaluacion`/`EntregaSemanal` — **no Rule 6 gate fired**, design §9.2). Public API added to `app/controllers/Tratamiento/index.ts`:

- `EstructuraPaciente` (type) — `{ pacienteId, puedeMedir, esAdmin, centrosActivos: ReadonlyArray<CentroEnergetico>, etapas: ReadonlyArray<EtapaEstructura> }`. Root of `get_estructura_paciente`'s mapped jsonb.

- `MomentoMedicion` (type) — `'apertura' | 'seguimiento' | 'cierre' | 'cierre_automatico'`.
- `MedicionNoEditableMotivo` (type) — `'automatica' | 'otro_terapeuta' | 'no_es_ultima' | 'etapa_posterior_iniciada' | 'sin_asignacion'`.

The full PostgrestError envelope, preserved (unlike `Paciente/api/callUpdateRpc.ts`, which collapses to `error.message` and destroys `error.code`) so `mapMedicionError` can distinguish `40001` from `22023` and switch on `message` before `code` (the `42501` overload between `no_autorizado` and `medicion_no_editable`).

Calls `get_estructura_paciente` and maps the jsonb via the private `mapEstructuraPaciente`. Read-only — does not go through `callMedicionRpc` (no error-code branching needed for a 42501-only failure mode).
- `useRegistrarMedicion()` / `useEditarMedicion()` / `useCerrarEtapaConMedicion()` — mutation hooks, each returning `{ submit: (payload) => Promise<MedicionMutationResult<T>>, isSubmitting: boolean }` via the private `useMedicionMutation` (a deliberate 1:1 clone of `Paciente/api/useSubmitMutation` — that hook is not exported from `Paciente/index.ts`, so reaching into it would violate controllers Rule 1/3). Each wraps its own private RPC caller (`registrarMedicion`/`editarMedicion`/`cerrarEtapaConMedicion`, all built on the private `callMedicionRpc` tail) and its own private `Payload` type — callers pass an inline object literal shaped `{ etapaId, valores, medicionPreviaId }` / `{ medicionId, valores }` / `{ pacienteId, motivo, valores, medicionPreviaId }` (`valores` is the wire shape `serializeValoresMedicion` produces).

Filters the full output of `validarValoresMedicion` down to what the form should paint: only the errors of fields the user already touched, or all of them once `mostrarTodos` is `true` (after a submit attempt). Used by `FinalizarTratamientoDialog` so the closing measurement does not open with every field in red; enabling the submit keeps depending on the full error set.
- `validarValoresMedicion(valores: Record<string, string>, campos: ReadonlyArray<CampoMedicion>): Record<string, string>` — pure per-field validator (empty / non-numeric / non-integer / out-of-0-100-range). Shared by the Estructura tab (PR3) and `FinalizarTratamientoDialog`'s step 2 (PR4).
- `serializeValoresMedicion(valores: Record<string, string>, campos: ReadonlyArray<CampoMedicion>): ValoresMedicionWire` — converts typed form state into the `p_valores` jsonb the 3 write RPCs expect (`{ estructura_general: number, centros: ReadonlyArray<{ centro_id, valor }> }`). `ValoresMedicionWire` itself is NOT re-exported from the barrel (internal wire shape, mirrors the `SemanaContenido`/`EntregaPlanInsertRow` precedent of staying local to their util file).
- `mapMedicionError(error: MedicionRpcError): MedicionErrorUi` — single source of truth for the medicion-estructura error catalog. Switches on `message`, never on `code` alone (the `42501` overload). For `valores_invalidos` (22023), reads the offending `campo` from the JSON embedded in `error.details` — **not** from `error.hint`/`error.details` as separate wire fields — per the medir-chakras verification-deferral decision (the PostgREST hint/detail-surfacing probe had not run when this was built; if it later shows `hint` does surface as a separate field, that is an optional simplification, never a rework).

Internals private to the folder (never imported from outside): `utils/mapEstructuraPaciente.ts` (owns the private `EstructuraPacienteRaw` — **never** exported), `utils/mapMedicionError.ts`'s internal motivo/detail helpers, `api/callMedicionRpc.ts`, `api/useMedicionMutation.ts`, `api/fetchEstructuraPaciente.ts`, `api/registrarMedicion.ts`, `api/editarMedicion.ts`, `api/cerrarEtapaConMedicion.ts` (each with its own private `*Payload` type), and the `MedicionHistoriaRaw`/`MedicionValorRaw` raw types added to `utils/mapEtapasToHistoria.ts`.

**`Tratamiento` fields:**

| Field               | Type                            | Meaning                                                                                                           |
| ------------------- | ------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `id`                | `string`                        | Tratamiento id.                                                                                                   |
| `fechaInicio`       | `string \| null`                | ISO date the treatment started, or `null` if the etapa was created but has not started yet (`inicioTratamiento`). |
| `fechaFin`          | `string \| null`                | ISO date the treatment ended, or `null` if still active.                                                          |
| `diagnostico`       | `Diagnostico`                   | The clinical diagnosis driving the treatment (see `Diagnostico`).                                                 |
| `estado`            | `TRATAMIENTO_STATE`             | One of `ACTIVO`, `FINALIZADO`, `SUSPENDIDO`.                                                                      |
| `niveles`           | `ReadonlyArray<Nivel>`          | The monthly follow-up checkpoints.                                                                                |
| `entregasSemanales` | `ReadonlyArray<EntregaSemanal>` | The weekly content deliveries (one bundle per week of the plan).                                                  |

**`TRATAMIENTO_STATE` values:** `ACTIVO`, `FINALIZADO`, `SUSPENDIDO`.

**Nested shapes:**

- `Nivel` — `readonly id: string`, `readonly numeroNivel: number`, `readonly fechaSeguimientoEsperado: string | null` (`null` when the etapa has not started yet — `register_paciente` creates the niveles grid before `fecha_inicio` is set, DEC-3 `inicioTratamiento`), `readonly fechaSeguimientoReal: string | null`, `readonly observaciones: string | null`, `readonly evaluacion: Evaluacion | null`. Represents one monthly checkpoint and the evaluation answered at it (if any).
- `Evaluacion` — `readonly id: string`, `readonly score: number`, `readonly fechaRespuesta: string`. The paciente's answer to the nivel's self-assessment.
- `EntregaSemanal` — `id`, `fechaEntregada`, `fechaEntregaEsperada`, `contenido: ReadonlyArray<Contenido>`. One week's bundle of media. Per the post-2026-05-22 product decision (see `../ENTIDADES.md` §7), each weekly bundle is composed of one video + one audio piece (the manually-assigned text piece was retired in frasesAutomaticas/epic-0, Task 0.4 — see `FraseDerivada` below), and treatments last 8 or 16 weeks. Does **not** carry the week's derived phrases (see `FrasesPorSemana`, frasesAutomaticas/FRA-005) — a `frases` field existed here until FRA-005 deleted it as a dead, disagreeing duplicate.
- `FraseDerivada` — `readonly orden: number`, `readonly origen: 'causa' | 'algoritmo'`, `readonly texto: string`. One of the 3 phrases automatically derived per week from the etapa's causa/algoritmo (`[causa#(2k-1), algoritmo#k, causa#(2k)]` for week `k`), sourced from the `get_frases_del_tratamiento_activo` RPC and exposed only via `FrasesPorSemana`, keyed by número de semana. Missing/errored RPC data resolves to `frasesPorSemana: {}`, never `undefined`.

**When to use.**

- Whenever the screen, hook, or BE call needs to talk about "the plan of a paciente" as a whole — its progress, its remaining weeks, the next scheduled delivery, the next evaluation due. A `Tratamiento` is the right unit, not the individual `Nivel` or `EntregaSemanal`.
- Cross-link: the underlying database schema for this aggregate (etapas_tratamiento, niveles, entregas, nivel_evaluacion) is documented in [`../ENTIDADES.md`](../ENTIDADES.md). This entity is the in-app TypeScript projection of that schema.
